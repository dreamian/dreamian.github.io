병사 관리 — 버킷 연결 리스트와 O(1) Splice

July 9, 2026

1. 문제 요약

병사들을 관리하는 다섯 가지 연산을 지원해야 한다.

  • hire(mID, mTeam, mScore): 고유번호 mID, 소속팀 mTeam, 평판 점수 mScore인 병사를 고용한다.
  • fire(mID): 해당 병사를 해고한다.
  • updateSoldier(mID, mScore): 해당 병사의 평판 점수를 mScore로 변경한다.
  • updateTeam(mTeam, mChangeScore): 소속팀 전체의 평판 점수를 mChangeScore만큼 변경한다. 결과가 \([1, 5]\) 범위를 벗어나면 경계값으로 절단(clamp)한다.
  • bestSoldier(mTeam): 소속팀에서 평판 점수가 가장 높은 병사의 고유번호를 반환한다. 동점이면 고유번호가 가장 큰 병사를 반환한다.

제약은 \(1 \le mID \le 100{,}000\), \(1 \le mTeam \le 5\), \(1 \le mScore \le 5\), \(-4 \le mChangeScore \le 4\)이다.

2. 접근: 갱신의 단위와 자료구조의 단위를 일치시키기

원소 단위 갱신(updateSoldier)만 있다면 lazy deletion heap이나 위치 추적 heap으로 충분하다. 그러나 updateTeam은 팀 전체를 한 번에 바꾸는 그룹 단위 갱신이다. 이를 원소 단위 자료구조로 처리하면 호출마다 팀 크기에 비례하는 비용이 들어 최악의 경우 감당할 수 없다.

핵심 관찰은 상태 공간의 크기다. \(mTeam \in [1,5]\), \(mScore \in [1,5]\)이므로 (팀, 점수) 조합은 정확히 \(5 \times 5 = 25\)개다. 그리고 updateTeam은 원소 단위로 보면 대량 갱신이지만, 버킷 단위로 보면 “팀 \(t\)의 점수 \(s\) 버킷 전체가 점수 \(\text{clamp}(s + d)\) 버킷으로 이동”하는 최대 5회의 버킷 이동이다.

Tip설계 원칙

갱신이 원소 단위와 그룹 단위로 섞여 있고 값의 도메인이 작다면, 그룹 자체를 일급 객체로 만들어 그룹 이동을 \(O(1)\)로 처리한다. 여기서는 (팀, 점수) 버킷마다 이중 연결 리스트를 두고, updateTeam을 리스트 통째 이어붙이기(splice)로 구현한다.

각 연산의 비용은 다음과 같다.

  • hire: 버킷 리스트 끝에 노드 삽입, \(O(1)\)
  • fire: 이웃 포인터 수정으로 노드 제거, \(O(1)\)
  • updateSoldier: 제거 후 새 버킷에 삽입, \(O(1)\)
  • updateTeam: 버킷 splice \(\times\) 최대 5회, \(O(1)\)
  • bestSoldier: 점수 \(5 \to 1\) 순으로 첫 비어있지 않은 버킷을 찾고, 그 리스트를 순회하며 최대 ID 탐색, \(O(\text{버킷 크기})\)

bestSoldier만 선형이지만 나머지 전 연산이 \(O(1)\)이므로 전체 시간 안에 들어온다.

3. updateTeam의 순회 방향

같은 호출 안에서 “이번에 옮긴 버킷을 또 옮기는” 오염을 막으려면 순회 방향이 \(d\)의 부호에 따라 갈라져야 한다.

\(d > 0\)일 때 점수를 낮은 쪽(\(s = 1\))부터 처리하면, \(s=1\)의 병사들이 \(s = 1+d\)로 이동한 뒤 루프가 \(s = 1+d\)에 도달했을 때 다시 이동해버린다. 결과적으로 \(+d\)가 아니라 연쇄적으로 밀려 올라간다. 따라서:

  • \(d > 0\): 점수 \(5 \to 1\) 순서로 처리 (목적지 버킷이 이후에 다시 처리되지 않도록)
  • \(d < 0\): 점수 \(1 \to 5\) 순서로 처리
WarningSelf-splice 주의

경계 clamp 때문에 \(\text{clamp}(s + d) = s\)가 되는 버킷이 존재한다 (예: \(d > 0\)에서 \(s = 5\)). 자기 자신으로의 splice는 tail의 next가 자기 head를 가리키는 사이클을 즉시 만들므로, this == target이면 아무것도 하지 않고 반환해야 한다.

4. 센티널 노드: 편의가 아니라 정합성 요건

splice는 버킷을 통째로 옮기므로 각 노드가 기억하는 점수 필드는 갱신되지 않는다. 이것이 \(O(1)\)의 대가다. 그런데 노드의 점수가 stale하면 이후 fire/updateSoldier가 잘못된 리스트에 대해 삭제를 수행한다.

head/tail 포인터를 리스트 구조체가 직접 들고 있는 설계에서는 이 stale 참조가 치명적이다. 삭제 대상 노드가 실제 소속 리스트의 head나 tail인 경우, 이웃 포인터 수정은 노드를 통하므로 올바르게 동작하지만 head/tail 갱신은 엉뚱한 리스트에 반영된다. 실제 리스트의 head는 제거된 노드를 계속 가리키고, 그 노드가 다른 버킷에 재삽입되면 리스트 사이에 교차 링크가 생겨 순회가 사이클에 빠진다.

해법은 stale 점수를 동기화하는 것이 아니라(그러면 splice가 다시 선형이 된다), 삭제 연산이 소속 리스트를 아예 몰라도 되게 만드는 것이다. 각 버킷에 dummy head와 dummy tail 센티널을 두면 모든 실제 노드의 prev/next가 항상 non-null이 되고, 삭제는 이웃 포인터 두 개의 수정으로 끝난다.

[dummy_head] <-> n1 <-> n2 <-> ... <-> nk <-> [dummy_tail]
Important센티널이 문제를 구조적으로 소멸시키는 이유

삭제가 head/tail을 만지지 않으므로 “어느 리스트 소속인가”라는 질문 자체가 사라진다. 그 결과 노드의 점수 필드는 아무 연산도 참조하지 않게 되어 제거할 수 있다. 팀은 고용 이후 불변이므로 노드에 한 번만 기록하면 updateSoldier가 삽입할 버킷을 결정할 수 있다.

부수 효과로 splice의 두 분기(target이 비었을 때 / 아닐 때)도 통합된다. 빈 리스트에서도 dummy_tail.prev가 dummy_head를 가리키므로 동일한 포인터 조작이 양쪽 경우를 모두 처리한다.

NoteMove 계열 연산의 불변식

splice처럼 원소들을 다른 컨테이너로 이동시키는 연산은 완료 시 원본을 반드시 빈(consumed) 상태로 되돌려야 한다. 원본의 head/tail이 이동한 노드들을 계속 가리키면, 이후 원본에 대한 삽입이 다른 리스트 내부의 살아 있는 노드를 덮어쓰며 교차 링크와 사이클을 만든다. 분기가 여러 개라면 모든 분기에서 이 후처리가 빠짐없이 수행되는지 확인해야 한다.

5. 디버깅 기록

구현 과정에서 실제로 만난 버그들이며, 모두 포인터 기반 연결 리스트에서 반복적으로 등장하는 패턴이다.

  1. Self-splice로 인한 즉시 사이클. 경계 clamp에서 \(tsc = sc\)가 되는 경우를 걸러내지 않아, 자기 tail의 next가 자기 head를 가리키게 되었다.
  2. head 삭제 시 리스트 파괴. prev == nullptr인 노드를 지울 때 head = node->next가 아니라 head = nullptr로 설정하여 뒤따르는 노드 전체가 유실되었다.
  3. 삭제된 노드의 stale 포인터. 제거 시 노드의 prev/next를 리셋하지 않아, 재삽입된 노드가 이전 리스트로의 링크를 그대로 들고 있었다.
  4. stale 점수 필드 경유 오삭제. splice 후 점수 필드가 갱신되지 않은 노드를 삭제할 때 잘못된 리스트의 head/tail을 수정하여 교차 링크가 발생했다. 센티널 도입으로 근본 해결.
  5. splice의 분기 비대칭. target이 비어있지 않은 분기에서만 원본 리셋이 누락되어, 유령 참조를 가진 원본에 대한 후속 append가 다른 리스트를 오염시켰다.
  6. splice 내 점수 동기화 루프로 인한 TLE. stale 점수를 고치려고 splice에서 전 노드를 순회하자 updateTeam이 \(O(\text{팀 크기})\)로 퇴화했다. 동기화가 필요 없는 구조(센티널)로 전환하여 해결.
Tip방어벽 트랩의 효용

개발 중 리스트 불변식(tail->next == nullptr 등)을 검사하는 트랩을 심어두면, 침묵하며 진행되는 포인터 오염을 오염 시점 근처에서 노출시킬 수 있다. 순회 중 같은 노드 주소가 두 번 출력되는 것으로 사이클의 존재와 위치를 특정할 수 있었다. 제출 전에는 반드시 제거한다.

6. 복잡도

호출 횟수를 \(Q\), bestSoldier가 스캔하는 버킷 크기를 \(B\)라 하면:

\[ T = O(Q) + O\left(\sum_{\text{bestSoldier}} B\right) \]

bestSoldier를 제외한 모든 연산이 상수 시간이며, 메모리는 노드 배열 \(O(MAX\_SOLDIERS)\)와 센티널 포함 리스트 25개로 \(O(N)\)이다.

Codes

#define MAX_TEAM        (5)
#define MAX_SCORE       (5)
#define MAX_SOLDIERS    (100'001)

struct Node {
    Node* prev;
    Node* next;

    int s_id;
    int t_id;

    void init(int _sid, int _tid) {
        s_id = _sid;
        t_id = _tid;
        prev = next = nullptr;
    }
} node[MAX_SOLDIERS];

struct List {
    Node head;
    Node tail;

    void init() {
        head.prev = nullptr;
        head.next = &tail;
        tail.prev = &head;
        tail.next = nullptr;
    }

    bool is_empty() {
        return (head.next == &tail);
    }

    void append(Node* node) {
        node->prev = tail.prev;
        node->next = &tail;

        tail.prev->next = node;
        tail.prev = node;
    }

    void splice(List* target, int t_score) {
        if(this == target) return;
        if(is_empty()) return;

        Node* first = head.next;
        Node* last = tail.prev;

        Node* t_last = target->tail.prev;

        t_last->next = first;
        first->prev = t_last;

        last->next = &target->tail;
        target->tail.prev = last;

        init();
    }

    int get_best_sd() {
        int max_s_id = -1;
        for(auto nd = head.next; nd != &tail; nd = nd->next) {
            if(max_s_id < nd->s_id) {
                max_s_id = nd->s_id;
            }
        }
        return max_s_id;
    }
} m_list[MAX_TEAM][MAX_SCORE];

void mdelete(Node* node) {
    node->prev->next = node->next;
    node->next->prev = node->prev;
    node->prev = node->next = nullptr;
}

void init()
{
    for(int i = 0; i < MAX_TEAM; ++i) {
        for(int j = 0; j < MAX_SCORE; ++j) {
            m_list[i][j].init();
        }
    }
}

void hire(int mID, int mTeam, int mScore)
{
    --mTeam;
    --mScore;

    auto& target = node[mID];
    target.init(mID, mTeam);
    m_list[mTeam][mScore].append(&target);
}

void fire(int mID)
{
    auto& target = node[mID];
    mdelete(&target);
}

void updateSoldier(int mID, int mScore)
{
    --mScore;

    auto& target = node[mID];
    mdelete(&target);
    m_list[target.t_id][mScore].append(&target);
}

void updateTeam(int mTeam, int mChangeScore)
{
    --mTeam;

    if(mChangeScore < 0) {
        for(int sc = 0; sc < MAX_SCORE; ++sc) {
            int tsc = sc + mChangeScore;
            if(tsc < 0) tsc = 0;
            if(tsc >= MAX_SCORE) tsc = MAX_SCORE - 1;
            
            m_list[mTeam][sc].splice(&m_list[mTeam][tsc], tsc);
        }
    } else {
        for(int sc = MAX_SCORE - 1; sc >= 0; --sc) {
            int tsc = sc + mChangeScore;
            if(tsc < 0) tsc = 0;
            if(tsc >= MAX_SCORE) tsc = MAX_SCORE - 1;
            
            m_list[mTeam][sc].splice(&m_list[mTeam][tsc], tsc);
        }
    }
}

int bestSoldier(int mTeam)
{
    for(int sc = MAX_SCORE - 1; sc >= 0; --sc) {
        auto ret = m_list[mTeam - 1][sc].get_best_sd();
        if(ret != -1) return ret;
    }

    return -1;
}
