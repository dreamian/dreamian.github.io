청소부 최적화: greedy 정체에서 beam search로 3.3억 돌파하기

최적화
메타휴리스틱
Beam Search
Orienteering Problem
PS
밀도 greedy·메타휴리스틱이 322M에서 멈춘 이유, 하루 단위 분해와 beam search로 332M을 넘고, 2일 lookahead로 333M에 도달하기까지의 기록
공개

2026년 8월 27일

1 문제 정의와 채점기 모델

청소부가 \(100\times100\) 격자 위의 집들을 청소한다. 각 집에는 재료 \(m\in\{1,\dots,6\}\)가 있고, 그 집을 청소하면 가격 \(P_m\)을 얻는다. 하루는 720분이며, nextDay()를 최대 30번 호출할 수 있어 총 31개의 근무일 구간을 쓴다. 핵심은 위치가 날을 넘겨 이어진다는 점이다. 오늘 끝난 자리에서 내일이 시작한다.

한 번의 move(y,x) 호출은 다음 순서로 처리된다.

  • 이동: 맨해튼 거리만큼 시간 소모. 그 결과 \(>720\)이면 SCORE=0.
  • 청소: 목표 칸이 집이면 \(c_m=30m+30\)분 소모. 역시 \(>720\)이면 SCORE=0.
  • 보상: \(P_m\) 획득. 종료 시각이 480분을 넘겼다면 초과근무 보너스를 추가로 얻는다.
  • 이미 청소한 칸이나 빈 칸으로 이동하면 청소 보상은 없다.

가격과 청소시간, 그리고 청소 1분당 가치는 다음과 같다.

\(m\) \(c_m\) (청소분) \(P_m\) \(P_m/c_m\)
1 60 80,000 1,333
2 90 140,000 1,556
3 120 180,000 1,500
4 150 240,000 1,600
5 180 250,000 1,389
6 210 300,000 1,429
노트채점 구조의 함정

SCORE는 10개 테스트케이스에 걸쳐 누적되며, 한 번이라도 \(>720\)을 만들면 누적 SCORE가 0이 될 수 있다. 따라서 안전성은 점수보다 우선이다.

이 문제에서 가장 중요한 구현 원칙 중 하나는 다음과 같다.

시간 초과 가능성이 있는 이동을 절대 호출하지 않는다.

그래서 계획 단계에서 항상 newTime <= 720을 확인한 뒤 실제 move()를 실행한다.

2 정식화 — 시간종속 이익을 갖는 주기적 Orienteering Problem

이 문제는 Orienteering Problem(OP) — “예산 안에서 방문할 노드의 부분집합과 순서를 정해 수집 점수를 최대화” — 의 변형이다.

하루 내부에서 집 \(i\)에서 \(j\)로 이동할 때 필요한 시간은

\[ \tau(i,j)=d(i,j)+c_j \]

이다.

여기서 \(d(i,j)\)는 맨해튼 거리, \(c_j\)는 도착한 집 \(j\)의 청소시간이다.

따라서 코드에서 moveCost[i][j] 또는 더 명확하게 transitionTime[i][j]라고 부르는 값은 단순 이동거리만이 아니다.

\[ \boxed{ \text{transitionTime}[i][j] = \text{distance}(i,j) + \text{cleaningTime}(j) } \]

하루 최종 보상은 경로의 집 가격 합을 prize, 총 사용시간을 \(t\)라 하면

\[ \boxed{ \text{finalReward} = \text{prize} + 200\,(t-480)^+ } \]

로 볼 수 있다.

중요정식화가 준 결정적 통찰

목적함수는 하루별 기여의 합이고, 하루끼리 연결되는 핵심 정보는 다음 날의 시작 위치다.

즉 31일 전체를 한 번에 최적화하지 않고,

  1. 오늘 하루를 잘 푼다.
  2. 오늘 끝 위치를 다음 날로 넘긴다.

라는 분해가 가능하다.

3 1차 접근과 정체 — 그리고 잘못된 천장 결론

처음에는 전역 tour 하나를 만들고 하루로 잘라 담는 틀에서 여러 방법을 시도했다.

  • value-density greedy: 현재 위치에서 \(P_m/(\text{이동}+c_m)\)가 최대인 집을 탐욕적으로 선택 → 319.5M
  • GRASP: 무작위화 재시작
  • or-opt / 2-opt: 국소 탐색
  • LNS: destroy–repair
방법 SCORE
value-density greedy 319.5M
GRASP (RCL=3, 2000 restarts) 320.6M
or-opt 320.8M
강력 LNS (40k iters) 321.8M

다섯 방법이 전부 320~322M에 수렴했다. 이동 무시·밀도 knapsack 상한이 356M이었기에, “여러 방법이 같은 값에 수렴하니 322M 근처가 실질 천장”이라고 잘못 결론지었다.

경고이 결론은 틀렸다

여러 방법이 같은 값에 수렴하더라도, 그 방법들이 같은 해 표현과 같은 이웃구조를 공유한다면 독립적인 검증이 아니다.

여기서는 모두 “전역 tour + day packing”이라는 표현을 공유하고 있었고, 같은 basin에 갇혔다.

4 전환점 — 하루 단위 분해와 Beam Search

하루를 720분 예산의 작은 Orienteering Problem으로 보고 Beam Search로 풀었다.

핵심 구성은 다음과 같다.

  1. 전체 남은 집 중 오늘 볼 후보를 최대 63개로 축소
  2. 한 Beam 상태에서 다음 후보는 최대 16개만 확장
  3. 한 depth에서 살아남는 부분 경로는 최대 3800개
  4. 최대 방문 수는 12개
  5. 중간 pruning은 rank, 최종 하루 선택은 실제 finalReward

5 Beam Search의 의미

Beam Search에서 가장 헷갈리기 쉬운 세 파라미터는 다음과 같다.

#define CANDIDATE_COUNT 63
#define NEXT_COUNT 16
#define BEAM_WIDTH 3800

이 셋은 전혀 다른 의미다.

파라미터 의미
CANDIDATE_COUNT=63 오늘 탐색 대상으로 삼는 집의 수
NEXT_COUNT=16 하나의 부분 경로에서 다음 단계로 실제 확장할 자식 수
BEAM_WIDTH=3800 한 depth에서 동시에 살아남길 부분 경로의 수

즉 63개 경로를 유지하는 것이 아니다.

예를 들어 후보 집이 A,B,C,D,E이고 NEXT_COUNT=2, BEAM_WIDTH=3이라면:

depth 0
[]

depth 1
[A]
[B]

depth 2
[A→C]
[A→D]
[B→C]
[B→E]

4개 생성 → rank 상위 3개만 생존

Beam Width는 서로 다른 과거 경로를 얼마나 많이 기억할 것인가를 의미한다.

힌트Beam Width의 직관
  • BEAM_WIDTH가 작다 → 좋은 경로가 일찍 잘릴 수 있음
  • BEAM_WIDTH가 크다 → 탐색 다양성은 증가하지만 시간·메모리 비용 증가
  • 그러나 크다고 SCORE가 단조 증가하는 것은 아니다

중간 상태는 실제 SCORE가 아니라 불완전한 rank로 pruning하기 때문이다.

6 후보 사전선별 — 400개를 63개로 줄이기

하루마다 현재 위치 기준으로 다음 점수를 계산한다.

\[ \boxed{ \text{candidateScore} = P_m - \lambda c_m - \mu d } \]

채택값은

\[ \lambda=1450,\qquad \mu=1000 \]

이다.

score =
    PRICE[level]
    - CAND_LAMBDA * serviceTime
    - CAND_MU * distance;

하루 최대 청소 수는

\[ 720/60=12 \]

이므로 63개 후보는 실제 방문 수보다 충분히 넓다. 동시에 63개 이하이므로 방문 여부를 unsigned long long 하나로 저장할 수 있다.

unsigned long long visitedMask;

if (visitedMask & (1ULL << j)) {
    // already visited
}

6.1 왜 CAND_LAMBDA≈1450인가?

집의 청소시간 대비 가격은 대략 1333~1600점/분이다. 따라서 처음에는 “시간 1분의 기회비용”을 약 1500점으로 보는 것이 자연스럽다.

1450은 수학적으로 고정된 값이 아니라 합리적인 초기 스케일에서 실험으로 조정된 값이다.

6.2 왜 거리 계수는 1000인가?

후보 선정 단계에서 거리를 너무 강하게 벌주면 현재 위치 근처의 집만 후보에 남는다. 조금 먼 곳의 고가 집 군집을 발견하려면 거리 패널티는 청소시간 패널티보다 약하게 두는 편이 유리할 수 있다.

7 전이 비용 사전 계산

Beam 내부에서 매번 맨해튼 거리와 청소시간을 다시 계산하면 -O0 환경에서 비싸다.

그래서 하루 시작 시 다음을 미리 계산한다.

startCost[i]
moveCost[i][j]

실제 의미는:

\[ \text{startCost}[i] = d(\text{start},i) + c_i \]

\[ \text{moveCost}[i][j] = d(i,j) + c_j \]

이다.

따라서 moveCost라는 이름은 다소 오해의 여지가 있다. 학습용 코드라면 다음 이름이 더 명확하다.

transitionTime[from][to]
중요cost에는 청소시간이 이미 들어 있다

Beam 내부의

int cost =
    state.lastCandidate < 0
    ? startCost[nextCandidate]
    : moveCost[state.lastCandidate][nextCandidate];

에서 cost는 단순 이동거리가 아니다.

\[ \boxed{ cost = 이동시간 + 도착한 집의 청소시간 } \]

따라서

newTime = state.usedTime + cost;

는 채점기의 시간 증가와 정확히 대응한다.

8 Beam 상태 설계

상태는 다음 정보를 가진다.

struct BeamState {
    unsigned long long visitedMask;
    int prize;
    int rank;
    unsigned short usedTime;
    signed char lastCandidate;
    unsigned char routeLength;
    unsigned char route[MAX_DEPTH];
};

각 필드의 의미:

  • visitedMask: 후보 중 방문한 집 집합
  • prize: 집 가격 합
  • rank: Beam pruning용 평가값
  • usedTime: 오늘 사용한 시간
  • lastCandidate: 마지막으로 방문한 후보
  • route: 실제 실행할 경로

8.1 왜 MAX_DEPTH=12인가?

최소 청소시간이 60분이므로

\[ \boxed{ MAX\_DEPTH = 720/60 = 12 } \]

이다.

이 값은 튜닝값이 아니라 문제 제약에서 직접 도출된다.

9 한 Beam 상태에서 다음 후보 16개만 확장

후보 63개를 모두 검사하되 실제 자식 상태는 다음 점수가 높은 16개만 만든다.

\[ \boxed{ \text{nextScore}(j) = P_j - \nu\,\text{cost}_j } \]

채택값:

\[ \nu=1500 \]

choice.score =
    candidatePrice[nextCandidate]
    - NEXT_LAMBDA * cost;

여기서도 cost는 이동 + 청소시간이다.

NEXT_COUNT=16은 “한 상태가 다음에 얼마나 다양한 방향으로 갈 것인가”를 제어한다.

  • 너무 작으면 Greedy에 가까워진다.
  • 너무 크면 자식 상태를 너무 많이 만들고 대부분 바로 버린다.

10 Beam Width 3800의 의미

각 상태가 최대 16개의 자식을 생성하므로, 한 depth에서 최대

\[ 3800\times16 = 60,800 \]

개의 다음 상태가 생길 수 있다.

그 상태들을 rank 기준으로 정렬한 뒤 상위 3800개만 다음 depth로 넘긴다.

최대 60,800개 child
        ↓
rank 기준 pruning
        ↓
3,800개 survivor

즉 BEAM_WIDTH는 현재까지 서로 다른 경로 history를 몇 개까지 기억할 것인가를 결정한다.

11 초과근무 인지 rank

중간 상태 pruning에는 실제 점수가 아니라 다음 potential을 사용한다.

\[ \boxed{ \text{rank} = \text{prize} - 1500\min(t,480) - 1300(t-480)^+ } \]

480분 이전에는 시간 1분을 1500점의 기회비용으로 본다.

480분 이후에는 실제 보상에서 1분당 200점을 추가로 받으므로 실질 시간 비용을

\[ 1500-200=1300 \]

으로 낮춘다.

따라서 이 식은 사실상

\[ \text{rank} \approx \text{finalReward} - 1500t \]

로 해석할 수 있다.

노트rank와 finalReward는 역할이 다르다
  • rank: 어떤 중간 상태를 계속 탐색할지
  • finalReward: 어떤 완성된 하루 경로를 실제로 선택할지

탐색용 대리 목적과 실제 목적을 분리하는 것은 Beam Search에서 매우 중요하다.

12 왜 Beam Width를 크게 했는데 SCORE가 떨어질 수 있는가?

직관적으로는 Beam을 늘리면 기존 좋은 경로를 모두 포함하므로 SCORE가 올라갈 것 같지만, 휴리스틱 Beam Search에서는 보장되지 않는다.

12.1 이유 1 — rank는 실제 objective가 아니다

큰 Beam을 사용하면 이전에는 죽었던 많은 상태가 살아남는다. 그 상태들이 다음 depth에서 높은 rank의 자식을 대량 생성하면 기존 Beam에서 살아남던 경로가 오히려 밀려날 수 있다.

즉

\[ \boxed{ \text{More Search} \not\Rightarrow \text{Higher Score} } \]

이다.

12.2 이유 2 — NEXT_COUNT는 그대로다

BEAM_WIDTH만 크게 하고 NEXT_COUNT=16을 그대로 두면 모든 방향을 균형 있게 넓히는 것이 아니다. 많은 parent를 살리지만 각 parent는 여전히 같은 휴리스틱으로 고른 16개의 child만 만든다.

12.3 이유 3 — 2-day lookahead와의 불균형

오늘 Beam만 지나치게 강하게 하면 “오늘 점수가 높은 경로”가 Top-K를 점령할 수 있다. 하지만 그 경로들의 종료 위치가 내일 나쁠 수도 있다.

예를 들어:

오늘 A: 1,010,000 / 내일 800,000
오늘 B:   995,000 / 내일 1,000,000

2일 합은 B가 더 좋지만, TOPK=4에 B가 들어가지 못하면 내일 평가조차 해보지 못한다.

12.4 이유 4 — 런타임과 메모리 급증

BEAM_WIDTH=60,800이면 최대 child 수는

\[ 60,800\times16 = 972,800 \]

까지 증가한다.

-O0에서는 State 복사와 정렬 비용이 폭증한다.

13 Beam pruning 구현 — Merge Sort를 유지한 이유

생성된 상태를 rank 내림차순으로 정렬하기 위해 bottom-up merge sort를 사용했다.

stableSortStates(next, mergeBuffer, nextCount);
nextCount = beamWidth;

Min-Heap Top-K로 교체하는 것도 가능하고 이론적으로 목적에는 더 잘 맞는다. 하지만 시험 환경에서는 다음 이유로 merge sort를 유지하는 선택도 충분히 합리적이다.

  • 구현 원리가 단순하다.
  • 디버깅이 쉽다.
  • worst-case \(O(N\log N)\)이 명확하다.
  • stable한 결과를 얻기 쉽다.
  • 현재 시간 제한 안에 이미 들어온다.
힌트시험장에서는 “조금 더 빠른 코드”보다 “내가 확실히 구현 가능한 코드”가 중요하다

Min-Heap이 이론적으로 더 효율적이어도, 구현 리스크와 디버깅 시간을 고려하면 이미 통과 가능한 merge sort를 유지하는 것이 더 좋은 전략일 수 있다.

14 2-day Beam Lookahead

1-day Beam은 오늘만 최적화하므로 하루 끝 위치가 내일에 미치는 영향을 충분히 반영하지 못한다.

그래서 오늘의 상위 TOPK 경로 각각에 대해:

\[ \boxed{ \text{todayReward} + \text{estimatedTomorrowReward} } \]

를 계산한다.

채택값:

#define TOPK 4
#define LA_BEAM 400

오늘은 폭 3800의 full Beam으로 탐색하지만, 내일은 실제 실행할 경로가 아니라 미래 가치를 추정하는 용도이므로 폭 400의 작은 Beam을 사용한다.

오늘: 정확하게 탐색
↓
오늘 Top-4 후보

각 후보에 대해:
오늘 route를 실행했다고 가정
↓
내일 작은 Beam(400)
↓
today + tomorrow 비교

실제로 내일이 되면 전날 예측한 route를 강제 실행하지 않고 다시 full Beam으로 재계산한다. 즉 rolling horizon 방식이다.

15 2일 Lookahead의 apply → evaluate → undo 패턴

오늘 후보 \(r\)을 평가할 때:

  1. 오늘 방문할 집들을 임시로 active=0
  2. 그 상태에서 내일 Beam Search
  3. 예상 내일 reward 확보
  4. 오늘 집들을 다시 active=1

한다.

apply
→ evaluate
→ undo

이 패턴은 DFS, local search, simulated annealing, lookahead에서 매우 자주 사용된다.

16 Lookahead 결과

Beam 추정 lookahead의 score–시간 프론티어:

설정 (\(K\), LA_BEAM) SCORE \(-O0\) 시간
없음 (base) 332.10M 6.9s
(4, 400) — 채택 333.03M 9.3s
(8, 1000) 333.09M 19s
(10, 2000) 333.41M 36s

더 무거운 lookahead는 점수를 계속 올리지만 시간 제한을 넘는다. 따라서 약 10초 예산에서는 \((4,400)\)이 현실적인 절충이다.

힌트추정기의 편향이 방향을 가른다

내일 보상을 Greedy로 추정했을 때는 오히려 점수가 하락했다. 반면 작은 Beam으로 추정하면 개선됐다.

미래 추정기는 실제 해법과 비슷한 inductive bias를 가져야 한다.

이다.

21 같은 탐색 예산에서 Beam과 Next의 차이

다음 두 설정은 최대 자식 수가 같다.

A: Beam=2000, Next=16
B: Beam=4000, Next=8

둘 다:

\[ 32,000 \]

개의 child를 만들 수 있다.

하지만 의미는 다르다.

  • A: 적은 history에서 다양한 다음 선택
  • B: 많은 history를 유지하되 각 history에서 적은 선택

현재 문제는 경로 history가 중요하므로 NEXT_COUNT를 너무 작게 만들지 않는 선에서 Beam Width에 더 많은 예산을 주는 전략이 잘 맞을 수 있다.

22 시험장에서의 구현 순서

완성형 코드를 처음부터 한 번에 작성하려 하면 매우 어렵다. 이 문제의 최종 코드는 여러 단계의 개선 결과로 보는 것이 맞다.

22.1 V0 — 안전한 Greedy

현재 위치에서
price - λ*(이동+청소)
가 좋은 집 선택

먼저 SCORE가 0이 아닌 제출 가능한 baseline을 만든다.

22.2 V1 — 후보 축소

전체 집
→ 유망 후보 30~60개

22.3 V2 — 작은 Beam

처음에는:

CANDIDATE_COUNT = 30;
NEXT_COUNT = 4;
BEAM_WIDTH = 100;

정도로 구현한다.

22.4 V3 — rank 추가

처음에는:

rank = prize - 1500 * time;

처럼 단순하게 시작한다.

22.5 V4 — 초과근무 반영

PRE_LAMBDA = 1500;
POST_LAMBDA = 1300;

22.6 V5 — 전이시간 사전 계산

distance + cleaning

반복 계산 제거.

22.7 V6 — NEXT Top-K

각 상태에서 모든 후보를 child로 만들지 않고 상위 몇 개만 실제 확장.

22.8 V7 — Beam 폭 증가

100 → 300 → 600 → 1000 → 2000 → ...

22.9 V8 — 2-day lookahead

1-day Beam이 안정적으로 돌아간 뒤 마지막 고득점 개선으로 붙인다.

중요시험장의 핵심 전략

처음부터 333M 코드를 작성하는 것이 목표가 아니다.

항상 실행 가능한 버전을 유지하면서 한 단계씩 SCORE를 올린다.

Greedy
→ Candidate pruning
→ Small Beam
→ Better rank
→ Precompute
→ Larger Beam
→ Lookahead

이 순서가 훨씬 안전하다.

23 복잡도·메모리 분석

기호:

  • \(N\): 집 수 (\(\le400\))
  • \(C\): 후보 수 (63)
  • \(B\): Beam 폭 (3800)
  • \(R\): 상태당 실제 확장 수 (NEXT_COUNT=16)
  • \(L\): 최대 depth (12)

23.1 후보 검사

각 Beam 상태에서 최대 \(C\)개의 후보를 검사하므로:

\[ O(LBC) \]

현재 값:

\[ 12\times3800\times63 \approx 2.87\times10^6 \]

후보 검사 수준이다.

23.2 자식 생성

최대:

\[ O(LBR) \]

이며 한 depth에서 최대:

\[ 3800\times16 = 60,800 \]

개의 child가 생성된다.

23.3 정렬

각 depth에서 child 상태를 merge sort하므로 대략:

\[ O(BR\log(BR)) \]

비용이 추가된다.

23.4 Lookahead

하루 main Beam 한 번 + 오늘 Top-K 각각에 대해 작은 Beam을 수행한다.

main beam: width 3800
lookahead: TOPK=4 × width 400

24 메모리 분석 시 주의

기존 merge sort 구현에서는 다음 세 배열이 크다.

stateA[MAX_NEXT_STATE]
stateB[MAX_NEXT_STATE]
mergeBuffer[MAX_NEXT_STATE]

여기서:

\[ MAX\_NEXT\_STATE = BEAM\_WIDTH \times NEXT\_COUNT = 60,800 \]

이다.

전역 배열이므로 스택 1MB 제약에는 직접 걸리지 않는다.

25 천장 진단 — 이동이 유일한 지렛대

Beam 해의 점수를 성분 분해하면:

성분 값 여지
초과근무 14.86M ≈ 이론상 최대 14.88M 거의 없음
유휴 88분 거의 없음
이동 15,182분 핵심 개선 대상

초과근무와 유휴가 거의 포화되어 있다면 더 이상 “하루를 더 꽉 채우자”가 핵심이 아니다.

남은 지렛대는:

이동시간을 줄여 청소시간으로 바꾸는 것

이다.

이 분석이 2-day lookahead를 시도한 근거가 된다. 오늘 마지막 위치를 더 좋게 만들면 다음 날 첫 이동을 줄일 수 있기 때문이다.

26 왜 이겼고, 왜 이전 접근은 정체했는가?

Greedy, GRASP, 2-opt, LNS는 모두 서로 다른 알고리즘처럼 보였지만 사실 같은 표현을 공유했다.

전역 tour
+
day packing

따라서 같은 구조적 약점을 공유했다.

Beam Search의 가장 큰 개선은 파라미터가 아니라 문제 표현을 바꾼 것이다.

전역 tour 최적화
↓
하루 단위 작은 OP 최적화

이 한 번의 representation change가 이후의 모든 튜닝보다 더 큰 점수 상승을 만들었다.

29 최종 교훈

  1. 표현을 바꾸는 것이 파라미터를 바꾸는 것보다 강하다.
    전역 tour → 하루 단위 Beam이라는 표현 전환이 가장 큰 도약이었다.

  2. 상관된 방법의 수렴은 최적성의 증거가 아니다.
    같은 해 표현을 공유하는 알고리즘은 같은 basin에 갇힐 수 있다.

  3. 탐색량을 늘린다고 SCORE가 반드시 증가하지 않는다.
    불완전한 rank와 pruning이 존재하는 휴리스틱에서는 More Search ≠ Better Score다.

  4. Beam Width와 Candidate Count는 다르다.
    후보는 집의 수이고, Beam은 살아남는 부분 경로의 수다.

  5. cost의 의미를 정확히 읽어야 한다.
    이 문제의 transition cost는 이동거리뿐 아니라 도착 집의 청소시간까지 포함한다.

  6. 대리 목적과 실제 목적을 분리한다.
    pruning은 rank, 최종 선택은 finalReward.

  7. 파라미터는 외우지 말고 범위를 찾는 절차를 익힌다.
    coarse search → fine search → runtime frontier.

  8. 시험장에서는 항상 동작하는 버전을 유지한다.
    Greedy → 후보 축소 → 작은 Beam → 평가함수 → 최적화 → lookahead 순으로 발전시킨다.

  9. 이미 제한시간 안에 들어오는 단순한 구현은 강한 자산이다.
    merge sort가 이해하기 쉽고 충분히 빠르다면, 더 복잡한 Min-Heap으로 바꾸지 않는 선택도 좋은 최적화 전략이다.

  10. 점수형 문제의 실력은 완성 코드를 외우는 것이 아니라, 병목을 보고 다음 개선을 선택하는 능력이다.
