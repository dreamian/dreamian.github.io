2 문제 정의와 채점기 모델

2.1 격자와 집

청소부는

[ 100 ]

격자 위를 이동한다.

집은 최대 약 400개 존재하며, 각 집은 등급

[ m{1,2,3,4,5,6} ]

을 가진다.

등급별 청소 시간은

[ service(m)=30(m+1) ]

이므로 다음과 같다.

등급 청소 시간 보상
1 60 80,000
2 90 140,000
3 120 180,000
4 150 240,000
5 180 250,000
6 210 300,000

코드에서는 다음 배열을 사용했다.

static const int PRICE[7] = {
    0,
    80000,
    140000,
    180000,
    240000,
    250000,
    300000
};

2.2 이동 비용

두 위치 사이의 이동 시간은 Manhattan distance다.

[ d((y_1,x_1),(y_2,x_2)) = |y_1-y_2|+|x_1-x_2| ]

집 (j)로 이동하여 청소하는 총 시간은

[ cost(i,j) = distance(i,j)+service(j) ]

이다.

따라서 전이 비용은 목적지 집의 service time을 포함하므로 비대칭 형태로 취급한다.

transition_cost[i][j]
=
abs(candidate[i].y - candidate[j].y)
+
abs(candidate[i].x - candidate[j].x)
+
service(candidate[j]);

격자 크기가 100이므로 최대 Manhattan distance는

[ 99+99=198 ]

이고 최대 service time은 210이다.

따라서 한 번의 전이는 최대

[ 198+210=408 ]

분이다.

2.3 하루 시간 제한

하루 제한은

[ 720 ]

분이다.

최소 청소 시간이 60분이므로 이동 시간을 완전히 무시하더라도 하루 최대 청소 집 수는

[ 720/60=12 ]

이다.

따라서 Beam의 최대 depth를

#define BEAM_DEPTH 12

로 둘 수 있다.

이러한 물리적인 상한을 먼저 계산하는 것이 중요하다.

탐색 depth를 막연히 20이나 30으로 잡을 이유가 없다.

즉 총

[ 31 ]

3 가장 중요한 채점기 특징: overtime이 패널티가 아니다

일반적인 스케줄링 문제라면 overtime은 패널티일 것 같지만 이 문제에서는 반대다.

480분을 초과한 작업 시간에 대해

[ +200 ]

점/분이 추가된다.

한 하루 route의 총 시간이 (T)라면 실제 reward는 사실상

[ Reward = PRICE + 200(0,T-480) ]

으로 계산할 수 있다.

따라서 480분을 넘는 것 자체를 무조건 피하면 안 된다.

다만 여기에서 매우 중요한 점이 있다.

실제 reward가 overtime에 +200을 준다고 해서 Beam rank에서도 반드시 overtime 시간을 +200만큼 높게 평가해야 하는 것은 아니다.

Beam rank는 실제 목적함수가 아니라 미래 좋은 상태를 살려두기 위한 surrogate objective이기 때문이다.

예를 들어 실제 reward에서는 현재 overtime 1분이 +200이더라도, Beam에서는 그 1분 때문에 다음 고가치 집 하나를 방문하지 못할 수 있다.

따라서 실제 reward와 Beam rank는 분리해서 생각해야 한다.

4 첫 접근: Greedy

가장 자연스러운 Greedy는 다음과 같다.

[ score(h) = PRICE_h - ,service_h - ,distance(current,h) ]

또는

[ {distance+service} ]

같은 효율 기반 평가를 사용할 수 있다.

이러한 Greedy는 구현이 매우 쉽고 빠르다.

하지만 점수가 약

[ 319M322M ]

근처에서 정체되었다.

5 Greedy가 정체되는 이유

Greedy는 현재 집 하나만 본다.

예를 들어 현재 위치에서

A: 매우 비싼 집 1개
B: 중간 가격 집 여러 개가 밀집된 지역

이 있다고 하자.

Greedy는 A를 선택하기 쉽다.

하지만 실제 하루 route 전체로 보면

현재 → B1 → B2 → B3 → B4

처럼 밀집 지역을 연결하는 것이 더 높은 점수를 줄 수 있다.

즉 이 문제는 사실상 하루마다 작은 Orienteering Problem을 반복해서 푸는 구조다.

7 Beam Search의 상태

사용한 상태는 다음과 같다.

struct BeamState {
    unsigned char route[BEAM_DEPTH];
    unsigned long long visit_mask;

    int prize;
    int rank;

    short used_time;

    signed char last;
    unsigned char route_len;
};

주요 정보는 다음과 같다.

route
    현재까지 방문한 candidate 순서

visit_mask
    방문한 후보 집 bitmask

prize
    집 가격의 누적합

used_time
    현재까지 소비한 시간

last
    마지막 candidate

rank
    Beam 생존용 surrogate score

후보를 최대 64개로 제한하므로

[ 64bit ]

정수 하나로 방문 집합을 저장할 수 있다.

이 구조는 -O0에서도 매우 중요하다.

bool visited[64], 동적 컨테이너, STL 등을 반복 복사하는 것보다 compact state를 통째로 복사하는 편이 빠르다.

8 Candidate를 먼저 줄여야 한다

집이 300~400개이고 각 Beam State마다 전부 확인하면 너무 비싸다.

따라서 먼저 전역 후보를 Top-64로 축소한다.

Candidate score는

[ C(h) = PRICE_h -_C service_h -_C distance(start,h) ]

를 사용했다.

최종값은

TODAY_LAMBDA = 1400
TODAY_MU     = 900

Tomorrow 역시

LA_CAND_MU     = 900

이 좋았다.

그래서 128 candidate까지 지원하도록 2개의 64bit mask를 구현해서 실험했다.

14 local ranking을 매번 정렬하지 않기

초기 코드에서는 각 state마다 child score를 계산한 뒤 insertion sort로 Top-16을 골랐다.

Beam state가 수천 개이므로 이것이 반복되면 -O0 환경에서는 상당히 비싸다.

그런데 local score는

[ PRICE_j-cost(i,j) ]

이고, 현재 위치가 candidate (i)로 정해졌을 때 순서는 고정된다.

따라서 미리

cand_order[last + 1][...]

를 계산할 수 있다.

last = -1
    → 하루 시작 위치에서의 action order

last = 0
    → candidate 0에서의 action order

...

last = 63

각 state에서는 precomputed order를 앞에서부터 읽으면서

이미 방문했는가?
시간 제한을 넘는가?

만 확인하고 feasible한 16개를 선택한다.

이 최적화는 반복 insertion sort를 제거해 runtime을 크게 줄였다.

45 Lazy Challenger Verification

Adaptive Top-2는 trigger될 때마다

2위 width1750 재평가

를 모두 수행한다.

따라서 계산을 더 줄이기 위해 다음 구조를 사용했다.

Champion = baseline 1위
Challenger = baseline 2위

gap <= 400이면

1. Challenger만 width=1750 재평가

2. Challenger가 Champion의
   baseline width=1270 점수도 못 넘으면
   → Champion 유지
   → 종료

3. Challenger가 잠정 역전하면
   그때만 Champion도 width=1750 재평가

4. 두 wide 평가를 최종 비교

수도코드는 다음과 같다.

champion = baseline_rank_1;
challenger = baseline_rank_2;

if (gap <= 400) {

    challenger_wide =
        evaluate(challenger, 1750);

    if (
        challenger_wide
        > champion_baseline
    ) {

        champion_wide =
            evaluate(champion, 1750);

        choose max(
            champion_wide,
            challenger_wide
        );
    }
}

고정 Tomorrow width를 크게 하는 실험에서는 1270 부근이 가장 좋았다.

]

이 더 좋았다.

즉 하나의 전역 최적 파라미터보다

가 더 좋은 것이다.

이것이 단순 parameter tuning에서 adaptive heuristic으로 넘어가는 지점이다.

50 이 문제에서 얻은 일반적인 휴리스틱 원칙

50.1 탐색량은 항상 좋은 것이 아니다

다음 모든 실험에서 동일한 현상이 나타났다.

Candidate 64 → 좋음
Candidate 128 → 나쁨

Next count 16 → 좋음
Next count 32 → 나쁨

Tomorrow width 1270 → 좋음
너무 큰 width → 나쁨

Top-K 6 → 좋음
더 큰 Top-K → 나쁨

Adaptive Top-K 2 → 좋음
3~6 → 계속 나쁨

원인은 approximate evaluation이다.

탐색 공간이 커질수록 좋은 후보도 늘지만 평가 오차에 노출되는 후보도 증가한다.

50.2 평가함수는 실제 목적함수와 같을 필요가 없다

Actual reward에는 overtime +200/min이 있다.

하지만 Beam rank에서 overtime을 직접 보상하는 것은 좋지 않았다.

휴리스틱의 평가함수는

현재 점수를 정확하게 표현하는 함수

가 아니라

미래에 좋은 최종 해로 이어질 상태를 잘 살리는 함수

여야 한다.

50.3 Candidate recall과 Beam precision을 분리한다

좋은 구조는 다음처럼 여러 단계로 후보를 줄이는 것이다.

전체 집 300~400
    ↓
Candidate Top-64
    ↓
State-specific Top-16 action
    ↓
Beam Top-3800
    ↓
DayPlan Top-6
    ↓
Tomorrow evaluation
    ↓
애매하면 Top-2만 재평가

한 번에 모든 것을 평가하려고 하면 느리고 noise도 커진다.

50.4 Tie는 절대로 사소하지 않다

휴리스틱에서는 동일 score가 매우 자주 발생한다.

따라서

stable order
generation order
route_len tie-break
candidate index

같은 작은 규칙도 실제 최종 SCORE에 영향을 줄 수 있다.

코드를 최적화할 때 기존 tie semantics를 보존해야 한다.

54 4시간 시험에서의 설계 전략

시험 시간이 4시간이라면 모든 아이디어를 구현할 수 없다.

가장 중요한 것은 정확한 순서로 시간을 쓰는 것이다.

54.1 0~30분: 채점기부터 읽는다

문제 설명보다 채점 코드를 먼저 본다.

반드시 확인해야 할 것은 다음과 같다.

실제 SCORE 식

상태가 다음 턴으로 무엇이 전달되는가
숨은 보너스/패널티
최대 입력 크기
최대 action 횟수

이 문제에서는 이 단계에서 바로 다음을 얻어야 한다.

하루 720분

이런 사실들이 이후 탐색 구조를 결정한다.

54.2 30~60분: 반드시 동작하는 Greedy를 만든다

첫 1시간 안에는 무조건 SCORE가 나오는 코드를 만든다.

예:

작동하는 320M 코드가 없는 상태에서 330M Beam을 설계하면 위험하다.

54.3 60~120분: 가장 큰 구조 개선 하나를 한다

이 문제에서는 Beam Search가 해당한다.

먼저 복잡한 lookahead를 넣지 말고

Candidate Top-L
State Top-N
Beam Width-W

의 하루 탐색을 완성한다.

시험에서는 처음부터 정확한 파라미터를 찾을 필요 없다.

예를 들어:

Candidate = 64
Next = 8~16
Beam = 500~2000

정도의 합리적 값을 사용한다.

이 단계에서 Greedy보다 큰 폭으로 올라가면 방향이 맞는 것이다.

54.4 120~180분: 미래가치를 추가한다

하루 Beam이 안정된 뒤에야 1-day lookahead를 추가한다.

Today Top-K
→ Tomorrow evaluator

형태다.

처음에는 Top-K를 작게 둔다.

K=2~4

정도로 시작하고 시간이 허락하면 늘린다.

중요한 원칙:

lookahead depth보다 evaluator의 신뢰성이 먼저다.

이번 문제에서도 day+2보다 정확한 Tomorrow 재평가가 훨씬 효과적이었다.

54.5 180~210분: 실행시간 최적화

점수가 충분히 좋아졌다면 탐색을 더 추가하기 전에 병목을 제거한다.

확인할 것은 다음과 같다.

매 state마다 정렬하고 있는가?
같은 cost를 반복 계산하는가?
큰 struct를 전체 sort하는가?
visited 배열을 반복 초기화하는가?
hypothetical state 전체를 backup하는가?
같은 future를 여러 번 계산하는가?

이 문제에서는

cand_order precompute
compact BeamState
RankKey quickselect
same_future cache

가 큰 효과를 냈다.

실행시간을 줄이면 그만큼 다시 탐색에 투자할 수 있다.

54.6 210~230분: adaptive 계산을 고려한다

모든 상태에 계산량을 늘리는 대신

이 방식은 4시간짜리 시험에서 매우 강력하다.

전체 알고리즘을 다시 만드는 것이 아니라 기존 evaluator 위에 작은 조건문으로 추가할 수 있기 때문이다.

54.7 마지막 10~30분: 새 구조를 만들지 않는다

마지막 시간에는 다음만 한다.

59 휴리스틱에서 자주 하는 실수

59.1 실제 목적함수를 그대로 rank로 쓴다

실제 SCORE와 같을 필요가 없다.

59.2 탐색량을 늘리면 무조건 좋아진다고 생각한다

Approximate evaluator에서는 오히려 나빠질 수 있다.

후보를 늘리면 recall은 올라가지만 winner’s curse도 증가한다.

59.4 parameter 하나의 최고점만 보고 확정한다

plateau와 testcase별 변화를 확인해야 한다.

59.5 코드 최적화에서 tie ordering을 바꾼다

점수가 달라질 수 있다.

59.6 미래 proxy를 직관만 믿고 사용한다

62 시험 직전 체크리스트

  1. 채점 코드에서 실제 목적함수와 illegal 조건부터 찾는다.
  2. 입력 크기에서 물리적인 탐색 depth 상한을 계산한다.
  3. 1시간 안에 합법적인 Greedy baseline을 만든다.
  4. 전역 후보 축소와 state별 branching을 분리한다.
  5. Beam rank와 실제 reward를 분리해서 생각한다.
  6. 탐색량을 늘렸을 때 점수가 떨어질 수 있음을 항상 가정한다.
  7. lookahead는 Today Top-K에만 사용한다.
  8. approximate evaluator에 너무 많은 후보를 노출하지 않는다.
  9. -O0에서는 반복 정렬, 큰 struct 복사, 동적 할당을 특히 경계한다.
  10. precompute, bitmask, compact state, Top-K selection을 적극 활용한다.
  11. 새 아이디어는 feature OFF에서 기존 SCORE가 재현되는지 먼저 확인한다.
  12. coarse sweep → fine sweep → boundary 분석 순으로 튜닝한다.
  13. 넓은 plateau는 robustness 신호로 본다.
  14. sharp peak는 Beam ordering boundary인지 확인한다.
  15. 깊은 탐색보다 가까운 evaluator의 품질을 먼저 개선한다.
  16. 계산량은 모든 후보가 아니라 uncertain decision에 집중한다.
  17. 상위 후보가 매우 가까우면 challenger verification을 고려한다.
  18. 총점뿐 아니라 testcase별 점수와 runtime을 기록한다.
  19. 마지막 20분에는 구조 변경보다 버그와 worst-case runtime을 점검한다.
  20. 최고의 휴리스틱 질문은 항상 이것이다.

“지금 추가로 쓸 수 있는 계산량을 어디에 투자해야 최종 선택이 가장 많이 개선되는가?”
