Open Addressing 해시 테이블의 삭제와 Tombstone

algorithm
hash table
선형 탐사 기반 해시 테이블에서 항목을 삭제할 때 탐사 체인이 끊기는 버그를 분석하고, Tombstone(묘비) 기법으로 해결하는 과정을 정리한다.
Published

May 25, 2026

1. 문제 개요

그룹 단위로 일정(event)을 등록·삭제·변경하는 시스템을 구현하는 문제이다. 네 개의 함수를 제공해야 한다.

  • addEvent(uid, ename, groupid) — groupid 그룹에 이름 ename인 일정을 등록한다. 그룹 내에 같은 이름의 일정이 없으면 master, 있으면 normal 상태가 된다.
  • deleteEvent(uid, ename) — 일정을 삭제한다. 삭제 대상이 master이면 같은 그룹·같은 이름의 일정이 모두 함께 삭제된다.
  • changeEvent(uid, ename, cname) — 일정 이름을 바꾼다. master이면 같은 이름 일정이 모두 함께 바뀌고, normal이면 변경된 일정이 새로 master가 된다.
  • getCount(uid) — 해당 유저에게 현재 등록된 일정 개수를 반환한다.

주요 제약은 다음과 같다.

  • 한 그룹의 일정은 최대 1000개, 그중 이름이 서로 다른 일정은 최대 200개, 같은 이름은 최대 5개.
  • 한 유저당 addEvent + changeEvent 호출은 최대 100회.
  • 전체 함수 호출 합은 최대 50,000회.

핵심은 “그룹 + 이름”으로 일정을 빠르게 찾는 것이므로, 그룹별 해시 테이블을 두는 설계가 자연스럽다.

2. 자료구조 설계

그룹마다 독립적인 해시 테이블을 둔다.

struct Event {
    char name[MAX_NAME_LEN];
    int  h_key;            // 슬롯 상태 겸 인덱스
    int  n_participants;
    int  participant[5];
} event[MAX_GRP][MAX_HKEY];
  • 해시 함수: djb2. 매 스텝 % MAX_HKEY로 누적해 [0, MAX_HKEY) 범위의 슬롯 인덱스를 얻는다.
  • 충돌 처리: open addressing + 선형 탐사(linear probing).
  • 유저 측 자료구조: 각 유저는 자신이 속한 일정 목록을 {gid, slot index, is_master}로 들고 있다.

여기서 중요한 설계 관찰이 하나 있다. 유저는 일정을 가리킬 때 슬롯 인덱스를 직접 저장하므로, “유저 → 일정” 조회(find_evt_idx)는 해시 탐사를 전혀 거치지 않는다. 해시 테이블의 탐사가 실제로 쓰이는 곳은 오직 addEvent 내부의 find / add뿐이다. 즉 버그가 숨을 수 있는 표면은 find/add 단 두 함수로 좁혀진다.

Note

디버깅에 들어가기 전에 “해시가 실제로 관여하는 코드 경로”를 먼저 좁혀두면, 원인 후보를 크게 줄일 수 있다. 자료구조가 인덱스를 직접 들고 있는 부분과 해시로 탐색하는 부분을 분리해서 보는 습관이 도움이 된다.

3. 버그: 삭제가 탐사 체인을 끊는다

처음 구현에서 일정 삭제는 슬롯을 완전히 초기화하는 방식이었다.

evt.init();   // name[0] = 0, h_key = -1, n_participants = 0

그런데 find의 탐사 종료 조건은 h_key == -1이다.

while (event[gid][h].h_key != -1 && cnt--) { ... }

init()이 h_key를 -1로 되돌리므로, 삭제된 슬롯은 “한 번도 쓰지 않은 빈 슬롯”과 구별이 불가능해진다. 선형 탐사에서 이는 치명적이다. 삭제된 슬롯이 어떤 항목의 탐사 경로 중간에 놓이면, 그 뒤에 있는 정상 항목이 검색에서 영구히 사라진다.

3.1 결정적 재현 시나리오

같은 그룹에서 두 이름 X, Y가 충돌해 hash(X) = hash(Y) = h라고 하자.

순서 호출 슬롯 상태 변화
1 addEvent(0, X, 0) X가 slot h에 저장 (master)
2 addEvent(0, Y, 0) slot h는 X → 탐사 → slot h+1에 Y 저장 (master)
3 deleteEvent(0, X) master 삭제 → slot h가 init()되어 h_key = -1
4 addEvent(1, Y, 0) find(Y): slot h에서 h_key == -1을 보고 즉시 nullptr 반환

4번이 핵심이다. Y는 slot h+1에 멀쩡히 살아 있는데, find가 slot h의 빈자리에서 탐사를 끊어버려 못 찾는다. 그 결과 add가 Y를 slot h에 새 master로 다시 만든다. 이제 그룹 0에 이름 Y인 일정이 slot h와 slot h+1 두 개로 쪼개진다.

이후는 연쇄적으로 무너진다. 유저 0은 slot h+1의 Y를, 유저 1은 slot h의 Y를 가리키게 되어 서로 같은 일정인데 다른 일정으로 인식한다. master가 둘이 되어 “master 삭제 시 동반 삭제” 의미가 깨지고, deleteEvent / changeEvent의 반환값과 getCount가 어긋난다.

Important

Open addressing에서 항목을 단순히 “빈 슬롯”으로 되돌리며 삭제하면 탐사 체인이 끊긴다. 이는 잘 알려진 함정이며, 삭제가 한 번이라도 일어나는 선형/이차 탐사 테이블에서는 반드시 별도 처리가 필요하다.

4. 왜 테이블을 키우면 “통과”하는가

처음에는 MAX_HKEY를 10007 → 100007로 키웠더니 통과했다. 하지만 이것은 버그를 고친 것이 아니라 가린 것이다.

슬롯 \(m\)개에 서로 다른 항목 \(n\)개를 넣을 때, 충돌이 하나라도 발생할 확률은 생일 문제(birthday problem)로 근사된다.

\[ P(\text{collision}) \;\approx\; 1 - \exp\!\left(-\frac{n(n-1)}{2m}\right) \]

그룹당 서로 다른 일정이 최대 \(n = 200\)개이므로,

\(m\) (MAX_HKEY) \(\dfrac{n(n-1)}{2m}\) 충돌 발생 확률
1007 \(\approx 19.8\) \(\approx 1.0\) (거의 확정)
10007 \(\approx 1.99\) \(\approx 0.86\)
100007 \(\approx 0.20\) \(\approx 0.18\)

10007에서는 충돌이 86%로 거의 항상 일어나고, 끊긴 체인을 밟을 확률도 그만큼 높아 실패한다. 100007에서는 충돌 자체가 18%로 드물어 테스트 데이터를 운 좋게 피한 것뿐이다. 채점 데이터가 바뀌면 100007에서도 깨질 수 있다.

이 문제의 채점 하네스는 시드 기반 의사난수로 문자열을 생성한다.

static int pseudo_rand(void) {
    mSeed = mSeed * 431345 + 2531999;
    return mSeed & 0x7FFFFFFF;
}

즉 충돌 패턴은 입력 데이터와 MAX_HKEY에 의해 결정되며, 테이블 크기를 바꾸는 것은 “어떤 데이터에서 깨지느냐”를 옮길 뿐 근본 원인을 건드리지 않는다.

Warning

어떤 상수(테이블 크기, 배열 여유분 등)를 키웠더니 버그가 사라졌다면, 거의 확실히 근본 원인이 따로 있다. “통과”는 정답의 증거가 아니라, 실패 조건을 우연히 피했다는 신호일 수 있다.

5. 해결: Tombstone (3-상태 슬롯)

해법은 슬롯을 세 가지 상태로 구분하는 것이다.

  • EMPTY — 한 번도 쓰지 않음. 탐사가 여기서 멈춰야 한다.
  • OCCUPIED — 항목이 들어 있음.
  • DELETED (tombstone) — 삭제됨. 탐사는 통과하되, 새 삽입 시 재활용 가능.

여기서는 별도 필드 없이 h_key 하나로 세 상태를 인코딩한다.

상태 h_key name[0]
EMPTY -1 0
DELETED -2 0
OCCUPIED ≥ 0 ≠ 0

init에 기본 인자를 주어 두 가지 초기화를 구분한다.

void init(int key_designated = -1) {
    name[0] = 0;
    h_key   = key_designated;   // 전체 초기화: -1(EMPTY), 삭제: -2(DELETED)
    n_participants = 0;
}

삭제 시 evt.init() 대신 evt.init(-2)를 호출하면 슬롯은 DELETED가 된다.

5.1 두 함수가 어떻게 협력하는가

  • find 의 종료 조건은 h_key != -1이다. DELETED(-2)는 -1이 아니므로 탐사를 통과하고, EMPTY(-1)에서만 멈춘다. DELETED 슬롯은 name[0] = 0이라 이름 비교에서 자연히 걸러진다. → 체인이 끊기지 않는다.
  • add 의 종료 조건은 name[0] != 0이다. DELETED 슬롯은 name[0] = 0이므로 add는 여기서 멈춰 빈 묘비를 재활용한다.

5.2 정확성의 근거

미묘하지만 중요한 불변식이 하나 있다. add는 단독으로 호출되지 않고, 항상 find가 nullptr을 반환한 직후에만 호출된다(addEvent 참고).

auto evt = find(groupid, ename);
if (evt == nullptr) { evt = add(groupid, ename); is_master = true; }

find는 EMPTY를 만날 때까지 탐사하며 모든 OCCUPIED 슬롯의 이름을 확인한다. 따라서 find가 nullptr을 반환했다면 그 이름은 테이블에 확실히 없다. 그 상태에서 add가 첫 번째 EMPTY 또는 DELETED 슬롯에 넣어도 중복은 생기지 않는다. 재활용 슬롯의 n_participants는 init이 0으로 비워두었으므로 잔여값 문제도 없다.

Note

add 자체는 “없으면 삽입”을 보장하지 않는다. tombstone을 만나면 그 자리에서 멈추므로, 만약 find 없이 add만 호출하도록 리팩터링하면 중복 삽입 버그가 생긴다. 이런 암묵적 호출 순서 의존성은 주석으로 명시해 두는 편이 안전하다.

5.3 작은 테이블이 오히려 증거가 된다

수정 후 MAX_HKEY를 1007로 줄여도 통과한다. 4절의 표에서 보았듯 1007에서는 충돌 확률이 사실상 1이다. 즉 충돌과 긴 탐사 체인이 거의 확정적으로 발생하는 환경인데도 정답이 나온다는 것은, tombstone이 충돌을 올바르게 처리하고 있다는 강한 증거다. 테이블 크기는 처음부터 원인이 아니었다.

6. PS에서 주의할 점

이번 디버깅에서 일반화할 수 있는 교훈을 정리한다.

Tip

1. Open addressing의 삭제는 반드시 tombstone. 선형/이차 탐사 테이블에서 항목을 단순히 비우면 탐사 체인이 끊긴다. 삭제가 일어나는 순간 EMPTY / OCCUPIED / DELETED 3-상태가 필요하다.

2. “상수를 키웠더니 통과”는 위험 신호. 테이블 크기·배열 여유분 같은 상수 조정으로 버그가 사라지면, 근본 원인이 따로 있을 가능성이 매우 높다. 확률적으로 가려졌을 뿐 다른 데이터에서 재발한다.

3. 충돌 의존 버그는 테이블을 극단적으로 줄여 강제 재현하라. 충돌이 의심되면 MAX_HKEY를 7~11처럼 아주 작게 두고 돌려보라. 충돌이 거의 확정적으로 일어나 버그가 결정적으로 재현된다. 큰 테이블에서 “가끔 틀림”을 쫓는 것보다 압도적으로 빠르다.

4. 시드 기반 하네스는 재현 도구다. 난수로 입력을 만드는 채점기는 시드가 같으면 입력도 같다. 실패하는 케이스의 시드를 고정하면 그대로 재현·디버깅할 수 있다.

5. 종료 조건(sentinel)을 일관되게 설계하라. 이번 버그의 본질은 find(h_key == -1)와 add(name[0] == 0)의 종료 조건이 삭제 후 어긋난 것이다. 탐사 기반 자료구조에서는 “어떤 상태에서 멈추는가”를 모든 연산에 걸쳐 일관되게 맞춰야 한다.

6. 삭제가 잦다면 체이닝도 고려하라. 연결 리스트 기반 체이닝은 삭제가 노드 제거로 끝나 tombstone이 필요 없다. 이 문제처럼 그룹당 항목이 200개로 작다면 체이닝이 더 단순하다. 구현 난이도와 메모리 지역성 사이의 트레이드오프를 의식적으로 선택하자.

```cpp #define MAX_GRP (100) #define MAX_USER (1000) #define MAX_NAME_LEN (16) #define MAX_HKEY (1007)

void mstrcpy(char dst[], const char src[]) { int c = 0; while ((dst[c] = src[c]) != 0) ++c; }

int mstrcmp(const char str1[], const char str2[]) { int c = 0; while (str1[c] != 0 && str1[c] == str2[c]) ++c; return str1[c] - str2[c]; }

unsigned long hash(const char str) { unsigned long hash = 5381; int c; while (c = str++) { hash = (((hash << 5) + hash) + c) % MAX_HKEY; } return hash % MAX_HKEY; }

struct Event { char name[MAX_NAME_LEN]; int h_key; int n_participants; int participant[5];

void delete_pid(int pid) {
    int i = 0;
    for (; i < n_participants; ++i) {
        if (participant[i] == pid) break;
    }
    participant[i] = participant[n_participants - 1];
    --n_participants;
}

// key_designated == -1 : EMPTY (전체 초기화)
// key_designated == -2 : DELETED (tombstone)
void init(int key_designated = -1) {
    name[0] = 0;
    h_key   = key_designated;
    n_participants = 0;
}

void add_participant(int pid) {
    participant[n_participants++] = pid;
}

} event[MAX_GRP][MAX_HKEY];

// EMPTY(h_key == -1)에서만 멈추고, DELETED(-2)는 통과한다. Event* find(int gid, const char *key) { unsigned long h = hash(key); int cnt = MAX_HKEY; while (event[gid][h].h_key != -1 && cnt–) { if (mstrcmp(event[gid][h].name, key) == 0) { return &event[gid][h]; } h = (h + 1) % MAX_HKEY; } return nullptr; }

// DELETED 슬롯(name[0] == 0)을 재활용한다. // 반드시 find가 nullptr을 반환한 직후에만 호출되어야 한다. Event* add(int gid, const char *key) { unsigned long h = hash(key); while (event[gid][h].name[0] != 0) { if (mstrcmp(event[gid][h].name, key) == 0) { return nullptr; } h = (h + 1) % MAX_HKEY; } mstrcpy(event[gid][h].name, key); event[gid][h].h_key = h; return &event[gid][h]; }

struct User { int n_events; struct { int key; int gid; bool is_master; } event_info[100];

void init() {
    n_events = 0;
}

void add_event(int gid, int event_key, bool master_flag) {
    event_info[n_events].key       = event_key;
    event_info[n_events].gid       = gid;
    event_info[n_events].is_master = master_flag;
    ++n_events;
}

void delete_event(int evt_id) {
    event_info[evt_id] = event_info[n_events - 1];
    --n_events;
}

int find_evt_idx(char ename[]) {
    for (int i = 0; i < n_events; ++i) {
        auto evt = &event[event_info[i].gid][event_info[i].key];
        if (mstrcmp(evt->name, ename) != 0) continue;
        return i;
    }
    return -1;
}

} user[MAX_USER];

void init() { for (int i = 0; i < MAX_USER; ++i) { user[i].init(); } for (int i = 0; i < MAX_GRP; ++i) { for (int j = 0; j < MAX_HKEY; ++j) { event[i][j].init(); } } }

void addEvent(int uid, char ename[], int groupid) { bool is_master = false; auto evt = find(groupid, ename); if (evt == nullptr) { evt = add(groupid, ename); is_master = true; } evt->add_participant(uid); user[uid].add_event(groupid, evt->h_key, is_master); }

int deleteEvent(int uid, char ename[]) { int evt_id = user[uid].find_evt_idx(ename); if (evt_id == -1) { return 0; }

int cnt = 1;
auto  target = user[uid].event_info[evt_id];
auto& evt    = event[target.gid][target.key];

user[uid].delete_event(evt_id);

if (target.is_master == true) {
    for (int i = 1; i < evt.n_participants; ++i) {
        int pid      = evt.participant[i];
        int nevt_id  = user[pid].find_evt_idx(ename);
        user[pid].delete_event(nevt_id);
        ++cnt;
    }
    evt.init(-2);   // tombstone
}
else {
    evt.delete_pid(uid);
}
return cnt;

}

int changeEvent(int uid, char ename[], char cname[]) { int evt_id = user[uid].find_evt_idx(ename); if (evt_id == -1) { return 0; }

int cnt = 1;
auto  target = user[uid].event_info[evt_id];
auto& evt    = event[target.gid][target.key];

user[uid].delete_event(evt_id);
addEvent(uid, cname, target.gid);

if (target.is_master == true) {
    for (int i = 1; i < evt.n_participants; ++i) {
        int pid     = evt.participant[i];
        int nevt_id = user[pid].find_evt_idx(ename);
        user[pid].delete_event(nevt_id);
        addEvent(pid, cname, target.gid);
        ++cnt;
    }
    evt.init(-2);   // tombstone
}
else {
    evt.delete_pid(uid);
}
return cnt;

}
