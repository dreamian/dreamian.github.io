1 Transport Layer 개요

1.1 계층 역할

Transport layer는 서로 다른 호스트에서 실행 중인 application process들 사이에 논리적 통신(logical communication)을 제공한다.

계층 역할
Network layer host ↔︎ host 사이의 논리적 통신
Transport layer process ↔︎ process 사이의 논리적 통신
  • 송신 측: App 메시지를 segment로 분할 → Network layer에 전달
  • 수신 측: Segment를 재조합 → App layer에 전달
Note비유: Household Analogy

Ann 집의 12명 아이들이 Bill 집의 12명에게 편지를 보낼 때:

  • Houses = hosts
  • Kids = processes
  • Letters = app messages
  • Ann/Bill (우편물 분류) = transport protocol (demux)
  • 우체국 = network-layer protocol

1.2 Internet Transport Protocol 비교

TCP UDP
신뢰성 신뢰적, 순서 보장 비신뢰적, 비순서
연결 Connection-oriented Connectionless
흐름 제어 ✅ Flow control ❌
혼잡 제어 ✅ Congestion control ❌
Header 크기 20 bytes 8 bytes
사용 예 HTTP, FTP, SMTP DNS, streaming, SNMP

2 Multiplexing & Demultiplexing

2.1 개념

  • Multiplexing (송신): 여러 소켓의 데이터에 transport header를 붙여 network layer로 전달
  • Demultiplexing (수신): header 정보를 이용해 수신 segment를 올바른 소켓으로 전달

2.2 UDP (Connectionless) Demux

  • 2-tuple: (dest IP, dest port) 만으로 소켓 식별
  • 출처(src IP, src port)가 달라도 동일 dest port → 동일 소켓으로 전달

2.3 TCP (Connection-oriented) Demux

  • 4-tuple: (src IP, src port, dest IP, dest port) 전부 사용
  • 동일한 dest port 80이라도 src가 다르면 다른 소켓으로 demux
Tip핵심 차이

TCP는 4-tuple 전체로 소켓을 식별하므로, 같은 서버 포트(80)에 연결된 서로 다른 클라이언트는 각자의 독립적인 소켓을 갖는다.

3 UDP (User Datagram Protocol)

3.1 Segment 구조

┌─────────────────┬──────────────────┐
│  source port #  │   dest port #    │  16 + 16 bits
├─────────────────┴──────────────────┤
│      length     │    checksum      │  16 + 16 bits
├────────────────────────────────────┤
│         application data           │
└────────────────────────────────────┘
  • length: UDP segment 전체 바이트 수 (header + data)

3.2 UDP를 사용하는 이유

  • No connection establishment → 지연 없음
  • No connection state → 서버가 더 많은 클라이언트 처리 가능
  • Small header (8 bytes vs TCP 20 bytes)
  • No congestion control → 원하는 속도로 전송 가능

3.3 UDP Checksum

3.3.1 계산 대상

단순히 “segment 전체”가 아니라, Pseudo Header + UDP Header + UDP Data를 모두 포함한다.

Pseudo Header (IP header에서 빌려온 필드):

┌─────────────────────────────────────────┐
│        Source IP Address (32 bits)      │
├─────────────────────────────────────────┤
│     Destination IP Address (32 bits)    │
├──────────────┬──────────────────────────┤
│  zero (8b)   │  Protocol=17 (8b)        │
├──────────────┴──────────────────────────┤
│           UDP Length (16 bits)          │
└─────────────────────────────────────────┘
Note왜 Pseudo Header를 포함하는가?

UDP header 자체에는 IP 주소 정보가 없다. Pseudo header를 포함함으로써 IP 주소가 바뀌는 오배송(wrong delivery)도 어느 정도 감지할 수 있다.

3.3.2 1의 보수(One’s Complement) 계산 방식

1의 보수: 모든 비트를 반전

0110 1010  →  1001 0101  (1의 보수)

성질: \(x + \sim x = \underbrace{1111\ldots1}_{\text{all ones}}\)

3.3.3 계산 예시 (두 16-bit 정수 합산)

  1111 0011 0011 0011 0         ← 첫 번째 값 (17비트, 맨 앞은 carry)
+ 1110 1010 1010 1010 1
─────────────────────────
  1101 1101 1101 1101 1         ← carry out 발생
                   + 1         ← wrap around (carry를 최하위에 더함)
─────────────────────────
  1101 1101 1101 1110 0         ← 최종 sum
  
Checksum = 1의 보수:
  0010 0010 0010 0001 1         ← checksum 값

3.3.4 에러 감지 메커니즘

수신 측에서: 수신된 모든 16-bit word + checksum을 합산

\[\text{sum} + \text{checksum} = \underbrace{1111\ldots1}_{\text{all ones}} \Rightarrow \text{에러 없음}\]

\[\text{sum} + \text{checksum} \neq \underbrace{1111\ldots1}_{\text{all ones}} \Rightarrow \text{에러 있음}\]

Warning한계

같은 비트 위치에서 짝수 개의 에러가 동시 발생하면 서로 상쇄되어 검출하지 못할 수 있다. (best-effort 에러 감지)

4 Principles of Reliable Data Transfer (rdt)

4.1 발전 과정 요약

버전 추가된 메커니즘 해결한 문제
rdt 1.0 - 완전 신뢰 채널 (trivial)
rdt 2.0 checksum, ACK/NAK 비트 에러 감지
rdt 2.1 Sequence number (0,1) ACK/NAK 손상 처리
rdt 2.2 NAK 제거, duplicate ACK NAK-free
rdt 3.0 Countdown timer 패킷 손실 처리

4.2 rdt 2.0 — 치명적 결함

ACK/NAK 자체가 손상되면 sender가 할 수 있는 것이 없다.

  • 재전송 → 수신 측에서 duplicate 가능성
  • → Sequence number로 해결 (rdt 2.1)

4.3 rdt 3.0 — Stop-and-Wait 성능 문제

\[U_{sender} = \frac{L/R}{RTT + L/R}\]

예시: 1 Gbps link, RTT = 30ms, L = 8000 bits

\[U_{sender} = \frac{0.008}{30.008} \approx 0.00027 \quad (0.027\%!)\]

→ 파이프라이닝 필요

4.3.1 rdt 3.0의 4가지 시나리오

시나리오 발생 원인 해결
(a) 정상 - 정상 동작
(b) Packet loss 패킷 유실 timeout → 재전송
(c) ACK loss ACK 유실 timeout → 재전송, receiver는 duplicate 감지 후 re-ACK
(d) Premature timeout ACK 지연 중복 전송되지만 seq#로 duplicate 처리

5 Pipelined Protocols

5.1 파이프라이닝으로 인한 성능 향상

3개 패킷 파이프라이닝 시:

\[U_{sender} = \frac{3 \cdot L/R}{RTT + L/R}\]

→ 3배 성능 향상

5.2 Go-Back-N (GBN) vs Selective Repeat (SR)

구분 GBN SR
Sender window N개 in-flight N개 in-flight
Receiver window 1 N
ACK 방식 Cumulative ACK 개별 ACK
Out-of-order 처리 Discard (버퍼링 없음) Buffer
재전송 범위 window 내 모든 unacked pkt 해당 pkt만
Timer oldest unacked pkt 하나 각 pkt 개별

6 Window Size 조건 — 핵심 개념

6.1 공통 원칙

두 프로토콜의 window size 조건은 동일한 원칙에서 출발한다:

\[\boxed{W_{sender} + W_{receiver} \leq \text{Seq\# space (N)}}\]

Sender가 재전송할 수 있는 seq# 범위와 Receiver가 “새 데이터”로 받아들이는 seq# 범위가 절대 겹치면 안 된다.

6.2 GBN 조건 도출

GBN에서 receiver window = 1이므로:

\[W + 1 \leq N \implies W \leq N - 1 = 2^k - 1\]

  • \(k\): seq# 비트 수, \(N = 2^k\): seq# 전체 공간

6.3 SR 조건 도출

SR에서 receiver window = sender window = W이므로:

\[W + W \leq N \implies W \leq \frac{N}{2}\]

Important두 조건의 관계

GBN의 조건(\(W \leq 2^k - 1\))이 SR의 조건(\(W \leq 2^k / 2\))보다 느슨하다. 이는 GBN의 receiver window가 1로 고정되어 있기 때문이다.

같은 원리(겹침 방지)에서 나왔지만, receiver window 크기 차이로 허용 가능한 sender window 크기가 달라진다.

6.4 SR Dilemma — 왜 N/2를 초과하면 문제인가?

6.4.1 원형 Seq# 공간으로 이해하기

Seq# 공간을 원형(circular) 시계판으로 상상한다. (N=4: 0,1,2,3)

🔴 W = 3 (> N/2 = 2) → 겹침 발생

Step 1: Sender [0,1,2] → pkt 0,1,2 전송 및 수신 완료
Step 2: ACK 0,1,2 모두 손실
        Receiver window 이동: [3,0,1]   ← 앞으로 이동
Step 3: Sender timeout → pkt 0 재전송

결과: 재전송된 seq# 0이 receiver window [3,0,1]에 포함됨!
      Receiver: "새 데이터로 오수락" ❌
       0  ← 재전송
     /   \
   3       1
     \   /
       2

Receiver window = [3, 0, 1]  ← 0이 포함됨 (겹침!)
Sender window   = [0, 1, 2]

🟢 W = 2 (= N/2) → 겹침 없음

Step 1: Sender [0,1] → pkt 0,1 전송 및 수신 완료
Step 2: ACK 0,1 모두 손실
        Receiver window 이동: [2,3]   ← 반대편으로 이동
Step 3: Sender timeout → pkt 0 재전송

결과: 재전송된 seq# 0이 receiver window [2,3] 밖!
      Receiver: "old data → 무시" ✅
       0  ← 재전송
     /   \
   3       1
     \   /
       2

Receiver window = [2, 3]  ← 0이 없음 (겹침 없음!)
Sender window   = [0, 1]

6.4.2 기하학적 이해

원형 공간에서 두 window의 합이 N을 초과하면 반드시 겹치는 부분이 생긴다.

\[2W > N \Rightarrow \text{두 호의 합} > \text{원 전체} \Rightarrow \text{겹침 불가피}\] \[2W \leq N \Rightarrow \text{원형 공간을 non-overlapping하게 분할 가능}\]

7 TCP

7.1 Segment 구조

┌──────────────────┬──────────────────┐
│   source port    │    dest port     │  16 + 16 bits
├──────────────────┴──────────────────┤
│           sequence number           │  32 bits
├─────────────────────────────────────┤
│         acknowledgement number      │  32 bits
├──────┬─────────────┬────────────────┤
│ hlen │  flags      │ receive window │
├──────┴─────────────┴────────────────┤
│  checksum  │   urg data pointer     │
├─────────────────────────────────────┤
│            options (variable)       │
├─────────────────────────────────────┤
│         application data            │
└─────────────────────────────────────┘

주요 플래그: URG, ACK, PSH, RST, SYN, FIN

7.2 TCP Sequence Number & ACK 이해

7.2.1 TCP는 “byte stream”

TCP는 패킷 단위가 아니라 연속된 바이트 스트림을 다룬다.

  • Seq#: segment에서 첫 번째 바이트의 번호
  • ACK#: 다음에 기대하는 바이트 번호 (= 지금까지 받은 마지막 바이트 + 1)
  • Cumulative ACK: “여기까지는 구멍 없이 다 받았다”는 누적 확인

7.2.2 Telnet 예시 (p.54)

초기 상태: A의 seq# 시작 = 42, B의 seq# 시작 = 79

A ──[Seq=42, ACK=79, data='C']──────────► B
  │                                       │
  │  Seq=42:  "내 데이터 첫 바이트는 42번"   │
  │  ACK=79:  "B의 79번 바이트를 기다림"     │
  │  data='C': 1바이트 전송                │

A ◄──[Seq=79, ACK=43, data='C']──────── B
  │                                       │
  │  Seq=79:  "내 데이터 첫 바이트는 79번"   │
  │  ACK=43:  "A의 42번(1바이트) 받음       │
  │            → 다음 43번을 기다림"        │

A ──[Seq=43, ACK=80]────────────────────► B
  │                                       │
  │  ACK=80:  "B의 79번(1바이트) 받음       │
  │            → 다음 80번을 기다림"        │
TipACK = Seq + data 크기인 이유

ACK#의 의미는 “X번째 바이트를 원한다” = “X-1번까지 모두 받았다”이다. 따라서 Seq=42, 1바이트를 받으면 → ACK=43 (42+1).

7.3 RTT 추정

7.3.1 EWMA (Exponentially Weighted Moving Average)

\[\text{EstimatedRTT} = (1-\alpha) \cdot \text{EstimatedRTT} + \alpha \cdot \text{SampleRTT}\]

\[\alpha = 0.125 \text{ (typical)}\]

과거 샘플의 영향이 지수적으로 감소 → 최근 측정값에 더 높은 가중치 부여.

7.3.2 편차(DevRTT) 추정

\[\text{DevRTT} = (1-\beta) \cdot \text{DevRTT} + \beta \cdot |\text{SampleRTT} - \text{EstimatedRTT}|\]

\[\beta = 0.25 \text{ (typical)}\]

7.3.3 Timeout Interval

\[\text{TimeoutInterval} = \text{EstimatedRTT} + 4 \cdot \text{DevRTT}\]

Note수학적 직관

\(\text{mean} + 4\sigma\) 형태로, 정규분포 가정 시 약 99.99% 신뢰구간에 해당한다. 변동성이 클수록 safety margin이 커진다.

7.3.4 왜 Retransmission은 RTT 측정에서 제외하는가?

Ambiguity 문제 (Karn’s Algorithm):

t=0:  pkt 전송 (seq=100)
t=5:  timeout → 재전송
t=8:  ACK(100) 도착

SampleRTT = ?
  원본 기준: 8 - 0 = 8ms  (실제보다 클 수 있음)
  재전송 기준: 8 - 5 = 3ms  (실제보다 작을 수 있음)
  → 어느 전송에 대한 ACK인지 알 수 없음!

잘못된 RTT 추정의 결과: - 과대 추정 → Timeout 너무 큼 → 재전송이 너무 느림 - 과소 추정 → Timeout 너무 작음 → 불필요한 재전송 폭발

7.4 TCP Reliable Data Transfer

7.4.1 재전송 트리거

  1. Timeout: 가장 오래된 unacked segment 재전송
  2. 3x Duplicate ACK: Fast Retransmit

7.4.2 ACK 생성 정책 (RFC 1122, 2581)

이벤트 수신 측 행동
순서 맞는 새 segment, pending ACK 없음 500ms 대기 후 ACK (Delayed ACK)
순서 맞는 새 segment, pending ACK 있음 즉시 cumulative ACK
Out-of-order segment (Gap 발생) 즉시 duplicate ACK
Gap 채우는 segment 도착 즉시 ACK

7.4.3 Cumulative ACK 이해 (p.62 상황)

Host A                              Host B

Seq=92  (8 bytes)  ──────────────►
Seq=100 (20 bytes) ──────────────►   ← ACK=100이 손실됨
                                     (B는 92, 100 둘 다 받아 buffer에 있음)
timeout 발생!
Seq=92 재전송 ────────────────────►

                             ◄──────  ACK=120

왜 ACK=120인가? B는 Seq=92(8 bytes)와 Seq=100(20 bytes)를 둘 다 buffer에 가지고 있으므로: - 92~99 (8 bytes) + 100~119 (20 bytes) = 119번까지 모두 수신 - → ACK=120: “120번째 바이트를 기다린다 (119번까지 구멍 없이 받았다)”

Cumulative ACK의 장점: ACK=100이 손실되더라도, 나중에 ACK=120 하나만 도착하면 100~119 전체가 정상 수신됐음을 알 수 있다.

7.4.4 Fast Retransmit

3개의 duplicate ACK → timeout 기다리지 않고 즉시 재전송

A ──[Seq=92]─────────────────────────────► B
A ──[Seq=100]──────────────── X (손실)
A ──[Seq=120]────────────────────────────► B
A ──[Seq=140]────────────────────────────► B

B ◄──────────────────── ACK=100 (dup)
B ◄──────────────────── ACK=100 (dup)
B ◄──────────────────── ACK=100 (dup)  ← 3번째!

A: timeout 기다리지 않고 Seq=100 즉시 재전송

7.5 TCP Flow Control

7.5.1 목적

수신 측 buffer overflow 방지 (cf. Congestion control은 네트워크 보호)

7.5.2 핵심 변수

\[\text{rwnd} = \text{RcvBuffer} - [\text{LastByteRcvd} - \text{LastByteRead}]\]

  • RcvBuffer: 수신 버퍼 전체 크기 (기본 4096 bytes)
  • LastByteRcvd: 마지막으로 수신된 바이트 번호
  • LastByteRead: Application이 마지막으로 읽어간 바이트 번호

Receiver는 모든 TCP segment header에 rwnd 값을 광고한다.

Sender 제약: \[\text{LastByteSent} - \text{LastByteAcked} \leq \text{rwnd}\]

7.5.3 rwnd = 0 엣지 케이스

Receiver가 rwnd=0을 광고하면 sender는 전송을 멈춘다. 이후 buffer가 비워져도 sender는 모른다 (trigger 없음).

해결책: sender는 주기적으로 1 byte probe segment를 전송. Receiver의 ACK에 실린 새 rwnd 값으로 재개 여부를 판단.

7.5.4 Flow Control vs Congestion Control

구분 Flow Control Congestion Control
보호 대상 수신 측 buffer 네트워크 전체
신호 rwnd (receiver → sender) packet loss, delay
메커니즘 rwnd로 sender 속도 제한 cwnd로 sender 속도 제한
실제 제한 min(rwnd, cwnd)로 동시에 작용

7.6 TCP Connection Management

7.6.1 3-way Handshake

Client                              Server
  │──[SYN, Seq=x]──────────────────►│
  │◄─[SYNACK, Seq=y, ACK=x+1]───────│
  │──[ACK, ACK=y+1]────────────────►│

Client state: CLOSED → SYN_SENT → ESTAB
Server state: LISTEN → SYN_RCVD → ESTAB

2-way handshake를 쓰지 않는 이유: 네트워크 지연, 재전송, 메시지 재순서 문제로 half-open connection이 생길 수 있음.

7.6.2 Connection Teardown

Client              Server
  │──[FIN]──────────►│   Client: FIN_WAIT_1 → FIN_WAIT_2
  │◄─[ACK]───────────│   Server: CLOSE_WAIT
  │◄─[FIN]───────────│   Server: LAST_ACK
  │──[ACK]──────────►│   Client: TIMED_WAIT (2×MSL 대기) → CLOSED
                         Server: CLOSED

TIMED_WAIT: 2 × MSL(Maximum Segment Lifetime) 동안 대기. 지연 도착한 duplicate segment를 처리하기 위함.

8 Principles of Congestion Control

8.1 혼잡(Congestion)이란?

“너무 많은 source가 너무 많은 데이터를 너무 빠르게 전송해서 네트워크가 처리하지 못하는 상태”

Flow control과의 차이: - Flow control: 수신 측 buffer 보호 - Congestion control: 네트워크 전체 보호

8.2 혼잡의 비용 (3 시나리오)

8.2.1 Scenario 2 핵심: Goodput vs Throughput

Perfect knowledge (이상적): 손실된 패킷만 재전송

lin' = R/2로 전송 시:
  = 새 데이터 + (실제 손실된 패킷 재전송)
  
손실 패킷은 라우터에서 drop됨 = 링크를 통과하지 못한 패킷
재전송은 그 자리를 채우는 것 → 링크 통과 총량은 여전히 R/2

∴ goodput ≈ R/2  (asymptotic)
Tipp.83의 의문 해소

“sending at R/2인데 goodput이 R/2인 이유?”

재전송이 필요한 패킷(실제 손실)을 보내는 것은 새 데이터를 보내는 것과 동등하다. 링크를 실제로 통과하는 총 데이터량은 여전히 R/2이다.

반면 premature timeout으로 인한 불필요한 중복 재전송은 bandwidth를 낭비하여 goodput < R/2가 된다.

Realistic (조기 timeout): 불필요한 재전송 포함

\[\text{goodput} < \frac{R}{2}\]

8.2.2 Scenario 3: Upstream 낭비

패킷이 다운스트림에서 drop되면, 업스트림에서 소비된 모든 전송 capacity가 낭비된다.

9 TCP Congestion Control

9.1 AIMD (Additive Increase Multiplicative Decrease)

  • Additive Increase: loss 없을 때 매 RTT마다 cwnd += 1 MSS
  • Multiplicative Decrease: loss 감지 시 cwnd = cwnd / 2

\[\text{sending rate} \approx \frac{\text{cwnd}}{\text{RTT}} \text{ bytes/sec}\]

9.2 Slow Start

  • 초기 cwnd = 1 MSS
  • 매 RTT마다 2배 증가 (ACK 수신마다 +1 MSS → 지수적)
  • ssthresh 도달 시 linear(CA) 모드로 전환

9.3 TCP Tahoe vs TCP Reno

9.3.1 공통 원칙

어떤 loss가 더 심각한가?

Timeout 3 Dup ACK
의미 네트워크가 심각하게 혼잡 하나 손실, 나머지 3개는 도착 → 덜 심각
판단 보수적 대응 필요 어느 정도 전송 능력 유지 가능

9.3.2 TCP Tahoe (1988)

어떤 loss든 무조건 보수적 대응:

Timeout  발생: cwnd = 1 MSS, ssthresh = cwnd_before/2, Slow Start 재시작
3 Dup ACK 발생: cwnd = 1 MSS, ssthresh = cwnd_before/2, Slow Start 재시작

9.3.3 TCP Reno (1990)

3 Dup ACK은 Fast Recovery로 차별화:

Timeout 발생:
  → cwnd = 1 MSS
  → ssthresh = cwnd / 2
  → Slow Start 재시작  (Tahoe와 동일)

3 Dup ACK 발생 (Fast Recovery):
  → ssthresh = cwnd / 2
  → cwnd = ssthresh + 3 MSS  ← 3개의 dup ACK = 3개 pkt 수신 의미
  → 손실 segment 재전송
  → 추가 dup ACK마다: cwnd += 1 MSS  (window inflation)
  → New ACK 도착: cwnd = ssthresh, CA 모드 진입
NoteWindow Inflation의 직관

Fast Recovery 중 추가 dup ACK이 올 때마다 cwnd += 1 MSS를 하는 이유:

각 dup ACK은 수신 측에서 패킷 1개가 더 빠져나갔음을 의미한다. 따라서 sender도 1개만큼 더 네트워크에 주입할 수 있다.

9.3.4 cwnd 변화 비교 시각화

cwnd │
     │      Tahoe                    Reno
     │    /                       /\
     │   /  3dup ACK             /  \      /
     │  /      ↓                /    \    /
     │ /     [1 MSS]           / 3dup ↓  /
     │/      slow start       /   [ssth+3]
     └──────────────────────────────────► time
     
Tahoe: loss → 항상 바닥(1 MSS)부터 재시작
Reno:  3dup → ssthresh 부근에서 유지, 더 빠른 복구

9.3.5 TCP 버전 발전사

버전 연도 핵심 특징

Reno 1990 Fast Recovery (3 dup ACK 차별화)
NewReno 1999 Reno의 partial ACK 문제 해결
CUBIC 2008 현재 Linux 기본, cubic 함수로 cwnd 증가

9.4 TCP Throughput 공식

Window size W 기반: \[\text{avg throughput} = \frac{3}{4} \cdot \frac{W}{\text{RTT}}\]

Loss 확률 L 기반 (Mathis 1997): \[\text{TCP throughput} = \frac{1.22 \cdot \text{MSS}}{\text{RTT} \cdot \sqrt{L}}\]

예: MSS=1500B, RTT=100ms, 목표 10 Gbps: \[L \leq 2 \times 10^{-10} \quad \text{(매우 낮은 loss rate 필요)}\]

9.5 TCP Fairness

K개의 TCP 연결이 bandwidth R을 공유 → 각각 R/K에 수렴

AIMD의 기하학적 직관: throughput 공간에서 “equal bandwidth” 라인으로 수렴하는 zigzag 경로 (additive increase = 기울기 1의 직선, multiplicative decrease = 원점 방향)

9.6 ECN (Explicit Congestion Notification)

  • IP 헤더의 ToS field 2비트를 라우터가 혼잡 시 마킹
  • 수신 측이 TCP ACK의 ECE bit 설정 → 송신자에게 혼잡 알림
  • 패킷 손실 없이 혼잡을 감지하는 메커니즘

10 무선 네트워크 관점에서의 시사점

Important무선 네트워크와 TCP의 근본적 문제

TCP Tahoe/Reno는 loss = congestion이라는 가정 하에 설계되었다.

그러나 무선 채널에서는: - 랜덤 비트 에러 → 손실 발생 (혼잡 아님!) - 핸드오버 → 순간적 연결 단절 - 채널 변동(fading) → 일시적 loss

TCP는 이를 모두 congestion으로 해석 → cwnd를 불필요하게 줄임 → 처리량 급감

이것이 BBR, CUBIC, 무선 특화 TCP 변형(예: TCP-Westwood, TCP-Veno)이 연구되는 핵심 동기이다.
