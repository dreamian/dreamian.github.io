ColO-RAN Paper Summary

Developing ML-based xApps for Open RAN Closed-loop Control on Programmable Experimental Platforms

Author

Polese, Doro, Bonati, Restuccia, Melodia (IEEE TMC, 2022) · arXiv:2112.09559

Published

June 23, 2026

1 One-line summary

The first systematic study to design, train, and validate a DRL xApp for O-RAN-based closed-loop control on a large-scale experimental platform . Three xApps were created to control RAN slicing and scheduling in real-time based on data, and were trained and evaluated with over 73 hours of full-stack data in an environment emulating actual wireless channels .

2 Problem Awareness — Why This Research Is Necessary

O-RAN standardized ML-based control as xApps on top of RIC, but the starting point is the lack of infrastructure as the actual reason for the slow progress of ML research. Five practical difficulties identified by the authors:

  1. Large-scale dataset collection — Lack of data reflecting the randomness of actual RANs
  2. Testing at Scale — Difficult to verify closed-loop control in a live network
  3. Incomplete Input / Constrained Output — Actual telemetry has irregular or missing periods
  4. Generalization — Adaptation to a deployment environment not present in training
  5. Feature Selection — Constructing meaningful state representations without dimension explosion

The core motivation is that because even telecommunications companies find it difficult to provide commercial networks for ML training/testing, research is confined to small-scale lab data and results are not generalizable.

3 ColO-RAN Platform Architecture

It is an experimental platform combining two axes.

3.1 Colosseum — wireless data factory

A large-scale wireless emulator built by DARPA. It reproduces actual fading and propagation characteristics in hardware-in-the-loop using multiple SDRs (USRP) and FPGA-based channel emulators (MCHEM) . It acts as a “data factory” that generates full-stack datasets in various RF scenarios .

3.2 O-RAN Infrastructure

near-RT RIC that runs on containers (LXC) by lightweighting the O-RAN Software Community (OSC) release . On the RAN side, it uses the SCOPE framework, an extension of srsRAN, as the CU/DU and connects to the RIC via the E2 interface. Because it is container-based, it can be ported to an indoor testbed (Arena) .

NoteExperiment scale

7 base stations · 42 UEs · 3 slices (eMBB / MTC / URLLC) · 10 MHz (50 PRB). Over 73 hours of collected data (approx. 3.4 GB).

4 xApp Design — Core of the Research

Designed three types of xApps.

xApp 3 types
xApp Control Method Action (Output)
sched-slicing Single DRL agent concurrently controls slicing + scheduling Number of PRBs per slice + scheduling policy
sched Parallel DRL agent per slice Scheduling policy per slice
online-training Online exploratory training on Live RAN Training Actions

4.1 DRL agent design

  • Algorithm: PPO (on-policy actor-critic). Training is slow because it uses only fresh data, but Reason that it is stable compared to off-policy(DQN).
  • Observation: rate, buffer size, number of PHY transport blocks, PRB ratio (DL standard). Intentionally reduced because learning slows down if the input dimension is large.

4.2 Autoencoder — Core Design Novelty

Instead of inputting the RAN telemetry as is, it is dimensionally reduced using an encoder (\(T \times N\) matrix → \(N\)-dimensional vector) and then passed to the DRL agent. Two effects:

  1. Dimensionality Reduction → Improved state→action mapping quality
  2. Robustness to missing telemetry → Intentionally using some entries of the input during training to maintain a meaningful state representation even if the input tensor is not fully filled during operation

This is a design that directly addresses problem awareness (3) (incomplete input) above.

4.3 Feature selection

Since O-RAN E2SM-KPM exposes hundreds of types of KPMs, redundancy is removed using a correlation matrix . For example, the number of transport blocks and the number of symbols have almost no correlation \(1.0\), so there is no need to include both, whereas the number of transport blocks and buffer occupancy have low correlation, so both are informative. Finally, number of transport blocks, buffer occupancy, DL rate, etc., are selected as inputs.

5 Key Experimental Results / Lessons Learned

  • Adaptive Control > Static Optimal Setting: sched-slicing that adjusts even slicing Superior to sched with fixed slicing. In particular, there was significant improvement in corner cases such as lower percentile users and PRB ratio.
  • Action space design determines performance: Agents with constrained action sets have biased policies Failed to maintain URLLC buffer/PRB ratio.
  • Autoencoder Effectiveness Proven: The agent with the autoencoder removed is the worst overall.
  • Trade-off in Online Learning: If a pre-trained model is additionally trained on a live network, it is deployed Performance improves as it adapts to the environment, but temporary performance degradation (disservice) occurs during the exploration phase.
  • Asymmetric Generalization: The agent generates well to changes in channel conditions but More vulnerable to traffic profile changes (entropy loss spikes more significantly upon traffic switching).

6 Research Gaps

Points not covered or left open by this paper. Serves as entry points for subsequent research.

6.1 Absence of prediction module

The DRL agent has a reactive structure that learns policies from the current state. There is no explicit predictive mechanism to predict future channel quality or traffic demand to preemptively allocate resources .

TipEntry point

channel quality prediction + traffic prediction as scheduler input (utility) to extend it into a predictive AI-RAN scheduler becomes a natural differentiating factor.

6.2 Vulnerability of Traffic Generalization (Acknowledged by the Author)

In the generalization experiment described in the text, the agent was robust to channel changes but ** performance fluctuated with traffic profile changes.** Traffic-aware / traffic-robust learning remains an unresolved issue.

6.3 Safety issues of online learning

online-training causes degradation of real-world service quality during the search process. Since this is difficult to tolerate in commercial networks, approaches to eliminate search costs through sim-to-real transitions or safe exploration are unavailable.

6.4 Coarse QoS granularity (coarse granularity)

Control remains at the slice / scheduling policy level. It does not handle fine-grained priority distinctions at the flow level, or further down to the application or semantic level.

6.5 Simplified synthetic traffic

Traffic is based on simplified synthetic models (full-buffer, etc.). Verification with actual application-driven traffic such as robot offloading and AI inference is outside the scope.

6.6 Absence of cross-layer signal

DRL input is limited to RAN telemetry. There is no cross-layer path where signals from the upper model layer (application/model layer) — such as the token importance (entropy, logprob, attention) of the generative model — come down to the L2 scheduler and are reflected in the utility.

6.7 Hardware stack limitations

Verification is based on SDR emulation (Colosseum + srsRAN). RAN + AI inference workload convergence on GPU-accelerated RAN (NVIDIA Aerial / cuMAC, GH200), i.e., real-time AI-RAN convergence, is not covered.

7 Synthesis — Link to follow-up research

ColO-RAN provides the standard architecture for DRL xApp-based closed-loop control. Combining the research gaps above, the differentiation axis for subsequent research is summarized as follows.

Cross-layer down from model layer signal (token importance) to MAC L2 resource allocation Mapping + Channel/Traffic Predictive Preemptive Scheduling + Actual GPU RAN Stack (cuMAC / GH200 / ROS2) Verification on top.

That is, while inheriting the autoencoder + DRL pipeline of ColO-RAN, the clear contribution is to (i) insert a prediction module to change the reactive to a preemptive one, (ii) replace synthetic traffic with actual robot/AI inference traffic , and (iii) move SDR emulation to a GPU-accelerated real stack .
